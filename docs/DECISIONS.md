# Decisions

Essential, hard-to-reverse decisions only. Not a changelog — if it's
obvious from reading the code, it doesn't belong here.

| Date | Decision | Why |
|------|----------|-----|
| 2026-11-03 | Backend: Go, stdlib `net/http`, no web framework | Go 1.22+'s built-in router covers method+path routing; a framework would add a dependency and indirection with no current benefit. |
| 2026-11-03 | DB access: `pgx` + `sqlc`, no ORM | Type-safe query results without ORM magic; SQL stays explicit, reviewable, and easy to reason about. |
| 2026-11-03 | Migrations: `golang-migrate`, SQL-first | De facto standard for Go; plain up/down SQL files, no DSL to learn. |
| 2026-11-03 | Frontend: Nuxt 3 + TypeScript | User requirement. |
| 2026-11-03 | No auth/multi-user in v1 | Single-user personal tool; auth is real complexity (sessions, password storage, authorization checks) that isn't needed yet — add it when a real multi-user need shows up. |
| 2026-11-03 | Docker Compose scope: Postgres only | Go and Nuxt both run fast natively for local dev; containerizing them adds build/rebuild overhead with no benefit at this stage. Compose is a dev convenience, not the deployment path. |
| 2026-11-03 | Money stored as integer cents, not floating point | Avoids floating-point rounding errors in financial amounts — standard practice. |
| 2026-11-03 | v1 scope: accounts, categories, transactions only (no budgets yet) | Budgeting is a distinct feature with its own data model (period, limits, rollover rules); building it speculatively before the core expense-tracking flow exists would be a speculative abstraction. Add when there's a working vertical slice to build it on top of. |
| 2026-11-03 | Budgeting is now in scope; one `recurring_definitions` table for all frequencies (monthly/quarterly/yearly) and kinds (income/expense) | Rent, bills, salary, and irregular costs don't differ structurally — only frequency changes. Two parallel models (e.g. "irregular" vs "monthly") would duplicate the same shape for no benefit. |
| 2026-11-03 | Account current balance is derived (starting balance + paid payments + manual adjustments), never a stored mutable counter | Avoids dual-write drift between a counter and the ledger; stays auditable; a `balance_adjustments` table gives the user an explicit, logged way to override/correct a balance without corrupting the derivation. |
| 2026-11-03 | Expected payment occurrences are generated lazily on read (idempotent upsert when an overview is fetched), not via a scheduled job | No cron/scheduler needed at this scale; keeps the backend stateless between requests and the stack boring. |
| 2026-11-03 | Monthly budget splits into "predicted costs" (fixed monthly expenses only) and "buffer" ((quarterly expenses / 3) + (yearly expenses / 12)); the two are summed only for the actual account transfer | Predicted costs is the figure to compare actual spending against; irregular (quarterly/yearly) costs are smoothed into a buffer that tops up the account every month regardless of whether a bill is actually due that month, so one isn't mistaken for the other. Supersedes the prior single blended "set-aside" figure, which still exists as the sum for the transfer amount. |
| 2026-11-03 | Migrations apply automatically on backend startup (`golang-migrate` as a library over an embedded FS), not via a manual CLI step | Flyway-style, requested directly; removes a manual setup step and keeps a container image self-contained. |
| 2026-11-03 | Docker Compose now also runs `backend` and `frontend` (supersedes "Postgres only") | Added as a one-command quick start; native `go run`/`npm run dev` remains the faster path for active development, so this is additive. |
| 2026-11-03 | "Set this month's budget" deposits the set-aside amount into a chosen account as a regular `balance_adjustments` row, tagged with a conventioned note (`"Monthly budget set-aside YYYY-MM"`) used to detect it was already applied | Reuses the existing adjustment mechanism instead of adding a budgets table; the note text is the idempotency marker, checked per month when building the monthly overview. |
| 2026-11-03 | `POST /data/clear` deletes every row in every table (payments, recurring definitions, balance adjustments, accounts, categories) and resets sequences, leaving a fully empty database | A partial wipe that kept accounts/categories was confusing ("clear data" left visible accounts behind); a full wipe matches user expectation and mirrors `/data/import`'s clear step, so there's only one definition of "empty" in the codebase. |
| 2026-11-03 | `GET /data/export` / `POST /data/import` exchange a full JSON snapshot (every row of every table, including ids and timestamps, versioned via a top-level `version` field); import unconditionally replaces ALL data, including `accounts` and `categories`, preserving ids across the round-trip and resetting sequences past the highest imported id | Gives the user a real backup/restore mechanism and a way to hand-edit data (e.g. remove a bad row) outside the DB; preserving ids keeps cross-table references valid without needing an id-remapping pass, and per-record delete endpoints were explicitly declined in favor of this edit-and-reimport workflow. |
| 2026-11-03 | Backend integration tests (`internal/api/*_test.go`) run against a real Postgres in an ephemeral container via `testcontainers-go`, one container per test binary run, isolated per test by truncating all tables; `internal/finance` gets plain unit tests (no DB) | Testcontainers is the standard way to test real DB behavior (constraints, cascades, sequences) in Go without touching the dev database or needing a hand-rolled container lifecycle; a shared container + per-test truncate is much faster than one container per test. |
| 2026-11-03 | Accounts get an `is_default` flag (exactly one, enforced by a partial unique index). Only the default account can be adjusted directly (`POST /accounts/{id}/adjustments`, sign-agnostic, no counterpart); every other account's balance only changes via `POST /transfers` — a pair of `balance_adjustments` rows (debit source, credit destination) inserted in one transaction, with both accounts chosen explicitly by the caller, not inferred. The monthly budget set-aside and the accounts-page "Add adjustment" form both use this (supersedes the prior single-sided deposit/correction on any account) | The default account is the only one fundable from outside the ledger (e.g. salary); crediting any other account without an offsetting debit would invent money, so funding a non-default account must be a real transfer with an explicitly chosen source — never silently assumed. |
| 2026-11-03 | Categories get a per-record `PATCH /categories/{id}` (rename) and `DELETE /categories/{id}`, plus a protected `is_default` category ("Others", `kind = expense`) that's lazily (re)created on `GET /categories` whenever none exists and can never be deleted | User-requested category management UI needs rename/delete; this narrowly supersedes the earlier "per-record delete endpoints declined in favor of edit-and-reimport" decision for categories only (not accounts/payments/recurring definitions). Deleting a category still fails with 400 if any payment or recurring definition references it (existing FK + `handleDBError` mapping, no new check needed) — "Others" exists so there's always a safe fallback category to re-point things at first. |
| 2026-11-03 | `recurring_definitions` gets a `tags text[] not null default '{}'` column; `GET /recurring?tag=<tag>` filters to definitions carrying that exact tag | Simplest way to support user-requested filtering of recurring payments by tag; a plain array column avoids a join table and rename/merge-tag endpoints that nothing has asked for yet — add a `tags` table later only if tag management (rename, autocomplete across definitions) becomes an actual need. |
| 2026-11-03 | `recurring_definitions.frequency` (enum `monthly`/`quarterly`/`yearly`) replaced by `interval_months integer` (any value >= 1); `quarterly` had no special status beyond being `interval_months = 3` | User wanted an arbitrary cadence (e.g. "every 2 months"), which a fixed 3-value enum can't express. `interval_months` already matched the internal occurrence-generation step size and the budget-buffer divisor, so this is a rename-and-generalize, not a new concept: monthly = 1, yearly = 12, any other positive integer is a custom interval, with no separate "quarterly" case in code. |
